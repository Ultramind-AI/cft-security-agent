# DynamicPlan v1

T14 introduces a structured planning boundary between hypothesis formation and the
existing `Validator -> Executor` path.

```text
Finding + Analysis + Hypothesis
        ↓
DynamicPlan
        ↓
DynamicPlanValidator (scope only)
        ↓
ActionProposal
        ↓
PolicyValidator
        ↓
Executor / Sandbox
```

## Contract

`DynamicPlan` contains:

- one verification goal;
- the current `hypothesis_id`;
- a bounded `max_steps` budget;
- optional current `sandbox_session_id`;
- explicit stop conditions and continuation reason;
- ordered `PlannedAction` entries;
- an expected observation and continue condition for every step.

Each `PlannedAction` contains the existing canonical `ActionProposal`. DynamicPlan
therefore does not create a second execution contract.

## Trust boundary

The LLM never supplies raw target, environment, URL, path or sandbox session fields
for a plan. It chooses only `candidate_id` values from candidates generated by code.
Code materializes the canonical `ActionProposal` fields from `TargetProfile` and,
when runtime observations are available, `RuntimeServiceMap`.

`DynamicPlanValidator` then verifies that:

- target/environment match the current `TargetProfile`;
- hypothesis matches the current workflow state;
- the plan fits the remaining iteration budget;
- sandbox session matches the current `RuntimeServiceMap`;
- referenced services exist in both target and runtime maps;
- referenced endpoints are allowlisted for the ready runtime service;
- action iterations follow plan order.

This validator is not execution permission. Every executed step still passes the
existing deterministic `PolicyValidator` immediately before `Executor`.

## T14 vs T15

T14 establishes the plan contract and produces multi-step plans. To preserve the
current workflow behavior, the graph executes only the first planned action today.
T15 will add the adaptive `observe -> reason -> act -> evidence` loop that chooses the
next planned step (or replans) from accumulated Evidence and stop reasons.
